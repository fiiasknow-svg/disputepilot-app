## 6. Buyer Q&A

### What exactly am I buying?

You are buying the DisputePilot software project and supporting sale-readiness materials. The package includes the root app code, tests, demo-safe data, documentation, deployment/env handoff notes, and buyer-facing commercialization materials. It does not include any credentials, private data, original-site credentials, or guaranteed customer revenue.

### Is it live?

The repo docs reference a live deployment URL, but buyers should verify the current deployment directly and plan to transfer or recreate infrastructure under buyer ownership. A live demo should be treated as a private demo environment, not proof of production launch readiness.

### Is it tested?

Yes. Existing docs report the latest known full local Chromium Playwright suite result as `358 passed`. The test suite covers many visible workflows and routes. Buyers should rerun tests from the exact handoff commit and add production/provider tests after completing billing, storage, email, and deployment integrations.

### Is it production-ready?

Not fully. It is best described as a tested SaaS starter platform. Production use requires buyer verification and hardening around billing, security/privacy, auth, Supabase/RLS/storage, provider accounts, deployment, live smoke tests, and legal/IP review.

### Does billing work?

Billing UI surfaces and tested visible workflows exist. Production payment processing, subscriptions, webhooks, entitlements, invoices, failed-payment handling, and live/test provider setup must be verified or completed by the buyer before charging customers.

### Can it be rebranded?

The app and docs are positioned around DisputePilot, and the sale-readiness packet includes branding/IP review materials. A buyer should still perform their own branding, trademark, copy, asset, and legal review before public launch.

### Is there IP risk?

There is always potential IP risk in a software acquisition, especially where prior audit materials or historical references exist. Existing docs identify branding/IP review as a required diligence area. Buyer-facing copy should avoid legacy/original-reference language, and buyer counsel should review before public launch.

### What accounts need to transfer?

The buyer should transfer or recreate the GitHub/repo ownership, Vercel deployment, Supabase project/storage, domain/DNS, OpenAI account if AI is used, Resend/email provider if email is used, payment provider if billing is implemented, and any other provider accounts selected for production.

### Can the buyer deploy it themselves?

Yes, the sale-readiness packet includes deployment/env handoff notes. A buyer should use buyer-owned infrastructure, configure environment variables, rotate secrets, run local tests, deploy a preview, and run live smoke tests before production use.

### What would it take to launch commercially?

The buyer should complete payment/subscription integration, security/privacy review, buyer-owned deployment, Supabase/RLS/storage verification, provider setup, live smoke testing, legal/IP review, onboarding docs, support process, pricing, and initial customer acquisition.

### What is included after purchase?

That depends on the final deal terms. A clean package should include the root project code, sale-readiness docs, handoff notes, demo script/materials, test instructions, known limitations, and any agreed handoff support. Credentials and private accounts should transfer securely outside git only if explicitly part of the deal.

1. 2 minutes: Confirm buyer goals and explain positioning.
2. 4 minutes: Dashboard, sidebar, clients, client profile.
3. 4 minutes: Leads, affiliates, public forms, and referral workflow.
4. 5 minutes: Disputes, dispute detail, letters, AI rewriter, documents, and contracts.
5. 4 minutes: Billing pages, calendar/reminders, company settings, portals/mobile.
6. 3 minutes: Automation/integrations, academy/help/training, and team areas.

8. 3 minutes: Known limitations and buyer diligence.
9. 1 minute: Next step: technical review, private offer, or second demo.

### What To Show

- Clean populated dashboard.
- Clients and client profile.
- Leads and affiliates.
- Disputes and dispute detail.
- Letters and AI rewriter surface.
- Billing pages as UI/workflow surfaces, with billing caveat.
- Calendar/reminders.
- Company settings.
- Portals/mobile app page.
- Automation/integration pages.
- Documents/forms/contracts.
- Sale-readiness docs folder.
- Testing summary showing latest known `358 passed`.

### What Not To Show

- Credentials, env files, local secrets, personal accounts, or password managers.
- Original-site credentials or internal original-reference materials.
- Unsanitized generated screenshots, traces, reports, or private browser tabs.
- Anything that implies current revenue, finished production billing, or fully verified security without evidence.
- Internal development noise unless the buyer specifically requests technical diligence.

### How To Disclose Limitations Without Killing Interest

Lead with the value of the asset, then disclose the next work clearly:

"The strongest part of this asset is that the buyer does not start from a blank repo. The app has broad workflow coverage, demo-safe data, test coverage, and handoff docs. The remaining work is the normal commercialization layer: buyer-owned deployment, payment integration, security/privacy review, provider setup, and launch hardening."
